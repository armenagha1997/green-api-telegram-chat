# Telegram Chat — тестовое задание GREEN-API

Веб-интерфейс чата для отправки и получения **текстовых** сообщений в Telegram через
[GREEN-API](https://green-api.com/). Выполнено по мотивам web.telegram.org.

Полная постановка задачи, ход разработки по этапам и технические решения — в [CLAUDE.md](./CLAUDE.md).

## Почему Telegram, а не MAX

Исходное ТЗ ориентировано на мессенджер MAX, но инстанс MAX создать не удалось. Раздел 3 ТЗ («Запасной
вариант») явно разрешает в этом случае использовать WhatsApp или Telegram — архитектура и жёсткие
требования (`SendMessage`, HTTP API вместо вебхуков, только текст) переносятся без изменений, различается
только раздел с деталями конкретного мессенджера. Подробности — в CLAUDE.md, раздел 3.

## Архитектура

```
src/
  api/        # greenApi.ts — фабрика createGreenApi(), types.ts — DTO и discriminated union уведомлений
  stores/     # AuthStore, ChatStore, PollingStore, RootStore (MobX)
  schemas/    # Zod-схемы форм (login, newChat, message)
  components/ # LoginForm, Sidebar, ChatListItem, NewChatModal, ChatWindow, MessageList, MessageBubble,
              # MessageInput, EmptyState — наблюдатели (observer), вся логика в сторах
  styles/     # SASS-переменные и глобальные стили
```

Компоненты не знают про конкретный мессенджер — весь доступ к API только через `src/api/greenApi.ts`.
Преобразование телефона в `chatId` инкапсулировано в `ChatStore.createChat()` через `CheckAccount`; если
понадобится вернуться к MAX или перейти на WhatsApp, меняется только этот модуль.

**Поток данных:**

- `AuthStore.login()` проверяет креды через `GetStateInstance` и требует статус `authorized`, сохраняет их
  в `localStorage`.
- После успешного входа `RootStore` (через `reaction` на `authStore.isAuthenticated`) запускает
  `PollingStore` и передаёт API-клиент в `ChatStore`.
- `PollingStore` крутит бесконечный цикл `ReceiveNotification → обработка → DeleteNotification` с
  `AbortController` и паузой при сетевых ошибках.
- `ChatStore.send()` отправляет сообщение оптимистично (сразу в статусе `sending`), после ответа API —
  `sent` с реальным `idMessage`, при ошибке — `error` с текстом причины и кнопкой «Повторить».
- Входящее сообщение от неизвестного `chatId` автоматически создаёт новый чат в списке.

## Особенности Telegram в GREEN-API

### `chatId` ≠ номер телефона

В Telegram `chatId` — числовая строка для личных чатов (`"10000000"`) и с минусом для групп
(`"-10000000000000"`), а не `79991234567@c.us`, как в WhatsApp. Поэтому при создании чата по номеру
телефона вызывается вспомогательный метод `CheckAccount`:

```
POST {apiUrl}/waInstance{idInstance}/checkAccount/{apiTokenInstance}
{ "phoneNumber": 79991234567 }
→ { "exist": true, "chatId": "10000000", "username": "@username" }
```

Дальше отправка и приём сообщений идут строго через `SendMessage` и `ReceiveNotification`/
`DeleteNotification`, как того требует ТЗ — `CheckAccount` используется только для резолва номера в
`chatId` один раз при создании чата.

Если `exist: false` — показываем ошибку «номер не зарегистрирован в Telegram». Это может означать и
реальное отсутствие аккаунта, и то, что у получателя приватность «Кто может найти меня по номеру»
ограничена его контактами.

### Ограничения на первый контакт

По документации и FAQ GREEN-API: аккаунту-инстансу разрешено не более ~50 новых чатов с незнакомыми
номерами в сутки, а `CheckAccount` не найдёт аккаунт, если у получателя приватность поиска по номеру
ограничена. **Для теста получатель должен заранее добавить номер инстанса в контакты Telegram** и/или
выставить приватность «Все» для поиска по номеру — иначе `CheckAccount`/`SendMessage` могут не сработать,
несмотря на `200 OK`.

## Настройка инстанса GREEN-API

1. Зарегистрироваться на [console.green-api.com](https://console.green-api.com), создать инстанс **Telegram**.
2. Авторизовать инстанс QR-кодом: Telegram на телефоне → Настройки → Устройства → «Привязать десктопное
   устройство», в консоли GREEN-API — «Получить QR» и отсканировать. Дождаться статуса `authorized`.
3. В настройках инстанса поле **Webhook URL должно быть пустым** (иначе `ReceiveNotification` вернёт 400).
4. Включить **«Получать уведомления о входящих сообщениях»** (`incomingWebhook: yes`) — без этого очередь
   уведомлений не наполняется, и `ReceiveNotification` всегда будет отвечать `null`.
5. Записать `apiUrl`, `idInstance`, `apiTokenInstance` — у каждого инстанса свой `apiUrl`
   (например `https://4100.api.green-api.com`), общего для всех инстансов адреса нет.

## Локальный запуск

### Через npm

```bash
npm install
npm run dev       # http://localhost:5173
```

`idInstance`/`apiTokenInstance`/`apiUrl` вводятся прямо на экране входа — отдельный `.env` для рантайма не
нужен (для справки есть `.env.example`, но приложение его не читает, значения вводятся через UI).

Другие команды:

```bash
npm run build            # прод-сборка
npm run lint              # ESLint
npm run format             # Prettier
npm run test               # Vitest unit-тесты (парсинг уведомлений, ChatStore)
npm run storybook           # Storybook на http://localhost:6006
```

### Через Docker

```bash
docker compose up --build   # http://localhost:8080
```

Multi-stage `Dockerfile`: сборка в `node:22-alpine`, раздача статики через `nginx:1.27-alpine`.

## Ограничения

- Только текстовые сообщения (по ТЗ) — остальные типы (картинки, стикеры, голосовые) молча удаляются из
  очереди без обработки.
- Чаты и сообщения хранятся только в памяти вкладки — при перезагрузке страницы история пропадает
  (сохраняются только креды входа в `localStorage`).
- `apiTokenInstance` нигде не логируется и не выводится в консоль.
- Один открытый инстанс = один Telegram-аккаунт. Привязка инстанса даёт GREEN-API полный доступ к
  аккаунту (как у любого другого связанного устройства) — для теста лучше использовать номер, которым не
  жалко рискнуть, а не основной личный аккаунт.
